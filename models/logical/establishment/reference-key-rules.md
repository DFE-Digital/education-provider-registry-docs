# Reference-data key rules

Each integer-keyed list in [Code lists](code-lists.md) has its own identity sequence, starting at 1 and incrementing by 1. Initial imports allocate consecutive IDs in business-code order. IDs are internal keys, independent of BAU codes.

| Column | Rule |
| --- | --- |
| Internal ID | Integer primary key; `GENERATED BY DEFAULT AS IDENTITY (START WITH 1 INCREMENT BY 1)`. |
| `code` | Required, unique BAU business code, retained even where it currently equals the internal ID. |
| `name` | Source label. |

Use integer `code` for plain-integer source codes. Preserve text codes, leading zeroes and alphabetic codes as text. UUID-keyed geographic lists and Diocese retain their existing identity design.

Relationships reference internal IDs. Migration resolves every relationship by business code. Existing IDs survive dictionary replay; new values use the next identity value. Do not renumber rows to close gaps after deletion or rollback.

Offline SQL fixtures restore explicit IDs. The rebuild then advances each sequence to the largest restored ID, so subsequent inserts cannot collide. Sequence configuration and initial consecutive populations are checked by `validate-reference-identities.sql`.

For establishment categories, internal IDs run from 1 to 11. Academies has internal ID 8 and BAU code 10. Category validation uses the business code, not a presumed internal ID.

Each code-list table over 50 rows is curtailed and labelled in the document. Geographic lists are last.
